# mcp-auto-control 方案设计

> 依据 `README.md` 编写。本文档描述如何把「鼠标 / 键盘自动控制」能力封装成本仓库的 MCP 服务端，
> 通过 MQTT 驱动两台 ESP32-S3 设备（AutoMouse、AutoKeyboard）。
>
> 文中所有固件侧协议与约束均来自实际源码核对（见 §3 的引用路径），不是推测。

---

## 1. 背景与目标

### 1.1 README 摘要

`mcp-auto-control` 提供自动控制功能：**鼠标移动、点击、滚轮滑动、键盘输入**。
实现依赖两个 ESP32 固件项目：

- ESP32 自动鼠标：AutoMouse
- ESP32 自动键盘：AutoKeyboard

两个仓库当前为私有/不可公开访问状态（GitHub 返回 404），本方案基于其本地源码：

| 项目 | 本地路径 | 形态 |
|---|---|---|
| AutoMouse | `E:/code/work/ljq/esp32/rust/AutoMouse` | `#![no_std]` 固件，枚举为 USB HID 鼠标 |
| AutoKeyboard | `E:/code/work/ljq/esp32/rust/AutoKeyboard` | 基于 RMK 的 `no_std` 固件，枚举为 USB HID 键盘（6×17 矩阵） |

两者的共同点：**联网后订阅一个 MQTT 主题，把收到的二进制报文直接注入自己的 HID 通道**，
即设备只负责「执行」，不负责「编排」。

### 1.2 本方案要解决的问题

目前要向设备下发动作，只能手工用 MQTT 客户端（如 Python `paho-mqtt`）拼二进制报文。
本方案把这条链路封装成 MCP 服务端，使 MCP 客户端（CodeBuddy Code 等）能以**工具调用**的方式：

- 表达高层意图（「移动到 (800, 600)」「输入文本 `hello@example.com`」「Ctrl+S」）
- 由服务端负责翻译成设备能接受的低层报文序列（位移拆分、修饰键、节流）

### 1.3 目标与非目标

**目标（v1）**

- 双设备：鼠标与键盘各自独立寻址，互不阻塞
- 覆盖 README 列出的四类动作：移动 / 点击 / 滚轮 / 键盘输入
- 服务端承担坐标语义转换、按键映射、节奏控制
- 保持 MCP stdio 传输，客户端只需配置一条命令即可接入

**非目标（v1 明确不做）**

- 不改动、不重写固件（对固件的改进建议见 §11，作为外部依赖列出）
- 不做屏幕截图 / 图像识别 / 元素定位（缺少感知输入，无此能力）
- 不支持非 ASCII 文本输入（受限于设备的 US ANSI 键位表，见 §6.4）
- 不做鉴权与加密（broker 为明文，见 §3.1）

## 2. 总体架构

### 2.1 分层

```
┌──────────────────────────────────────────────┐
│ MCP 客户端（CodeBuddy Code / Inspector）      │
└───────────────────┬──────────────────────────┘
                    │ MCP over stdio (JSON-RPC)
┌───────────────────▼──────────────────────────┐
│ mcp-auto-control（本仓库，Rust 二进制）        │
│                                              │
│  mcp 层      工具注册 / 参数校验 / 结果格式化  │
│   ▲                                          │
│  device 层   动作语义：位移拆分、按键映射、    │
│              虚拟光标、节奏控制               │
│   ▲                                          │
│  mqtt 层     连接管理、重连、报文编解码、发布  │
└───────────────────┬──────────────────────────┘
                    │ MQTT (TCP 1883, 明文)
┌───────────────────▼──────────────────────────┐
│ MQTT Broker（192.168.3.15:1883）              │
└──────┬────────────────────────────┬──────────┘
       │ topic: mouse/auto          │ topic: keyboard/auto
┌──────▼──────┐              ┌──────▼───────┐
│  AutoMouse  │              │ AutoKeyboard │
│  USB HID    │              │ USB HID      │
└──────┬──────┘              └──────┬───────┘
       │ USB                       │ USB
┌──────▼───────────────────────────▼──────────┐
│ 被控主机（OS 收到的是标准鼠标/键盘事件）       │
└─────────────────────────────────────────────┘
```

**关键点：服务端是纯发布者（publisher）。** 两个固件都只订阅、从不发布，因此服务端无需订阅任何主题，
也**无法从 MQTT 侧获得执行结果**（详见 §3.5 与 §10 的风险项）。

### 2.2 为什么服务端不能只做「透传」

MCP 客户端天然会给出高层意图，而设备只接受低层二进制：

| 客户端想说 | 设备能接受 | 服务端必须做的翻译 |
|---|---|---|
| 移动到 (800, 600) | `x`/`y` 是 **i8 相对增量** | 维护虚拟光标位置，拆成多帧 |
| 输入 `Hello` | 单个 HID KeyCode + 按下/松开 | `H` → 按住 LShift + `A` 键 … |
| 双击 | 两次 click | 时序控制（按下—松开—间隔—再按） |
| Ctrl+S | 一次只表达一个 key_code | 修饰键序列（按住 Ctrl → 按 S → 放 S → 放 Ctrl） |

这一层翻译是服务端的核心价值，也是工作量所在，故 `device` 层需要独立成模块并配单测。

## 3. 设备通信协议（对接契约）

### 3.1 MQTT 连接参数

两台设备固件中的连接参数完全一致，均为**编译期硬编码**（改网络需重新烧录）：

| 参数 | 值 | 来源 |
|---|---|---|
| Broker | `192.168.3.15`（仅支持 IPv4 字面量，不支持主机名） | `AutoMouse/src/mqtt.rs:16`、`AutoKeyboard/src/mqtt.rs:15` |
| Port | `1883`，**明文 TCP，无 TLS、无鉴权** | `mqtt.rs:17` / `mqtt.rs:16` |
| 协议版本 | MQTT **v5**（`rust-mqtt`，`clean_start`） | `mqtt.rs` `ConnectOptions::new().clean_start()` |
| 订阅主题（鼠标） | `mouse/auto` | `AutoMouse/src/mqtt.rs:19` |
| 订阅主题（键盘） | `keyboard/auto` | `AutoKeyboard/src/mqtt.rs:18` |
| Client ID | `AutoMouse` / `AutoKeyboard`（**固定值**） | 同上 |

两个后果需要提前接受：

1. **服务端的 client_id 必须另取**（如 `mcp-auto-control`），否则会把设备踢下线。
   同理，**服务端自身的多个实例之间也会互相踢下线**（同一台机器上 MCP 客户端可能
   并行拉起多个实例），因此实际使用的 client id 默认附加进程 PID，见 §7.1。
2. 同型号设备接入同一 broker 时会争抢会话（固件注释里已标 `TODO: 客户端ID-多设备时要注意`）。
   多块同型板子属于 v1 之外的范围，见 §10。

### 3.2 鼠标报文：`mouse/auto`

Payload **13 字节**，小端序：

| 偏移 | 长度 | 类型 | 字段 | 说明 |
|---|---|---|---|---|
| 0 | 8 | `u64` LE | `msg_id` | 关联 ID，固件**不解释**，仅用于日志 |
| 8 | 1 | `u8` | `buttons` | 位掩码 |
| 9 | 1 | `i8` | `x` | 水平**相对增量**，正数向右 |
| 10 | 1 | `i8` | `y` | 垂直**相对增量**，正数向下 |
| 11 | 1 | `i8` | `wheel` | 正数向上滚 |
| 12 | 1 | `i8` | `pan` | 正数向右滚 |

`buttons` 位掩码（`AutoMouse/src/hid/mod.rs:75-79`）：

| 位 | 值 | 按键 |
|---|---|---|
| 0 | `0x01` | 左键 |
| 1 | `0x02` | 右键 |
| 2 | `0x04` | 中键 |

⚠️ **必须发送完整 13 字节。** 固件在 `AutoMouse/src/mqtt.rs:147` 用 `payload.len() >= 10` 做长度校验，
但随后直接读取 `payload[10]`、`payload[11]`、`payload[12]`。发送 10~12 字节会触发
**切片越界 panic**（`panic_bounds_check`，不受 `release` 下 `overflow-checks = false` 影响），
且不会在日志里给出任何业务提示。已核实的后果链条：

1. 固件无自定义 panic handler，使用 esp-hal 的 `panic-handler` 特性（默认打印后停机）；
2. 停机会让 Embassy 执行器不再推进，`watchdog_task` 停止喂狗；
3. `TIMG1` 看门狗 Stage0 超时 **1 秒**、动作为 `ResetSystem`（`AutoMouse/src/bin/main.rs:81-88`），
   于是芯片直接复位 —— 表现为 USB HID 掉线重连。

服务端编码函数必须恒产出 13 字节，并由单测锁定。

### 3.3 键盘报文：`keyboard/auto`

Payload **10 字节**，小端序：

| 偏移 | 长度 | 类型 | 字段 | 说明 |
|---|---|---|---|---|
| 0 | 8 | `u64` LE | `msg_id` | 同上 |
| 8 | 1 | `u8` | `key_code` | HID KeyCode（usage id） |
| 9 | 1 | `u8` | `pressed` | `0` = 松开，非 0 = 按下 |

⚠️ **`key_code` 必须落在固件的 `KEY_MAPPING` 表内**，否则固件打印 `Invalid key code` 并忽略该消息
（`AutoKeyboard/src/mqtt.rs:153-168` → `AutoKeyboard/src/keymap.rs:448` 的 `key_code_to_pos`）。
不在表内的键（例如小键盘、多媒体键）**无法下发**。可用键集见 §6.4。

### 3.4 帧间节奏与背压

- 鼠标报文最终进入 `MOUSE_CHANNEL`（容量 8，`AutoMouse/src/hid/mod.rs:11`），由 `mouse_task` 独占消费写 USB。
- 设备侧 MQTT 接收循环是**串行且会阻塞**的：`hid::MOUSE_CHANNEL.send(report).await`（`AutoMouse/src/mqtt.rs:170`）
  在通道满时会挂起，此时 MQTT 任务不再 `poll()`。
- 因此过快的下发不是「丢帧在通道里」，而是**阻塞接收循环 → 后续报文在 broker / 设备 TCP 缓冲溢出后被丢弃**
  （QoS 0 无重传）；阻塞时间过长还会导致 MQTT keepalive 超时掉线，触发设备侧 10 s 重连。

服务端据此设定**默认帧间隔**（建议 10 ms，与固件 `button_task` 的 10 ms 轮询同量级），
并把「一次工具调用产生的报文数」纳入上限校验（§8）。

### 3.5 QoS、retain 与可靠性现状

| 决策 | 取值 | 理由 |
|---|---|---|
| QoS | `0`（默认，可配置为 1） | 固件未做 `msg_id` 去重（`README_CN.md` 明确「目前仅用于日志」）；QoS 1 重投只会重复按键，不会去重 |
| retain | `false` | 保留消息会在设备重连时被重放，等于「开机自动点一下」，是危险行为 |
| LWT / 状态主题 | **不存在** | 固件不发布任何消息，服务端无法判断设备在线、也无法收到执行确认 |

**这是本方案最大的结构性限制**：链路是「尽力而为的单向广播」。
`mqtt` 层能确认的只有「报文已交给 broker」，不能确认「设备已执行」。
对策见 §8.4（软确认）与 §11（固件侧改进建议）。

### 3.6 `msg_id` 生成规则

服务端使用进程内 `AtomicU64` 单调递增（从 1 开始）。

- 不落盘、不跨进程去重 —— 固件不用它去重，服务端也无需全局唯一。
- 作用是**排障**：设备串口日志会打印 `Received ...: msg_id=...`，可据此与 MCP 调用记录对账。

### 3.7 物理输入与远程输入共享同一通道（重要）

AutoMouse 的 `button_task`（`AutoMouse/src/bin/main.rs:175-197`）与 MQTT 任务写入**同一个** `MOUSE_CHANNEL`：

- 按住 GPIO2/GPIO4 任意按键时，设备每 10 ms 上报一次 `buttons=<物理按键>`、`x=2, y=2` 的报告；
- 即物理按键被按住期间，光标以约 **200 px/s 向右下漂移**，且这部分位移**服务端完全不知情**；
- 松开时上报一次 `buttons=0`、`x=0, y=0`。

由此产生两个必须在文档与工具描述中写明的边界：

1. **虚拟光标会在物理按键被按住期间失准**（§4.2、§10/R6）—— 自动控制期间不应有人去碰那两个按键。
2. **`emergency_stop` 无法解除物理按键**：它只能发送 `buttons=0` 的 MQTT 报文，
   而物理按键只要仍被按住，设备就会继续上报按下状态（§8.3）。

## 4. MCP 工具设计

工具名统一 `snake_case`，按域分组。参数结构体一律 `serde::Deserialize + schemars::JsonSchema`
（沿用现有 `Counter` 的做法，Schema 就是客户端看到的契约）。

### 4.1 工具清单

| 工具 | 域 | 输入 | 下发报文 |
|---|---|---|---|
| `mouse_move` | 鼠标 | `dx: i32, dy: i32` | N 帧（拆分） |
| `mouse_move_to` | 鼠标 | `x: i32, y: i32`（绝对坐标） | N 帧（拆分，依赖虚拟光标） |
| `mouse_move_smooth` | 鼠标 | `dx, dy, steps, duration_ms` | steps 帧（轨迹生成） |
| `mouse_click` | 鼠标 | `button: 枚举, count: u8, interval_ms` | 2×count 帧 |
| `mouse_press` / `mouse_release` | 鼠标 | `button: 枚举` | 1 帧 |
| `mouse_scroll` | 鼠标 | `delta: i32, axis: 垂直/水平` | N 帧 |
| `mouse_drag` | 鼠标 | `from, to, button` | 按住 + 轨迹 + 松开 |
| `mouse_position` | 鼠标 | — | 0 帧（读服务端虚拟坐标） |
| `keyboard_key` | 键盘 | `key: 字符串, action: 按下/松开/点击` | 1~2 帧 |
| `keyboard_combo` | 键盘 | `keys: [字符串]`（最后一个是主键） | 2×len 帧 |
| `keyboard_text` | 键盘 | `text: 字符串, interval_ms` | 2×字符数 帧 |
| `keyboard_release_all` | 键盘 | — | 松开所有已按下键 |
| `device_status` | 系统 | — | 0 帧（broker 连接状态 + 已按下集合） |
| `emergency_stop` | 系统 | — | 松开所有键 + 所有鼠标按钮 |

共 **15** 个工具（`mouse_press` / `mouse_release` 各算一个）。`emergency_stop` 是安全阀。

> **实现状态**：§4.1 的工具表已全部实现，见 §9 里程碑。
> 唯一签名调整：`mouse_move_smooth` 实现为 `(dx, dy, steps)`，**去掉了 `duration_ms`** ——
> 总耗时由 `steps × frame_interval` 决定。要更长耗时请调大 `--frame-interval-ms`，
> 而不是在一帧内等待，否则服务端会在等待期间白占动作序列锁。

### 4.2 坐标语义

设备的 `x`/`y` 是**相对增量**，没有绝对定位能力。服务端引入**虚拟光标**：

- 进程启动时虚拟坐标 = `(0, 0)`，由配置项 `MCP_MOUSE_ORIGIN`（可选）指定真实起点。
- 每次 `mouse_move(dx, dy)` 后累加；`mouse_move_to` 用「目标 − 虚拟坐标」求增量。
- 误差来自 OS 的指针加速/边界钳制：**虚拟坐标会漂移，这是已知的**。
  因此 `mouse_position` 的返回必须标注为「估计值」，并在描述里写明漂移风险。
- 需要绝对可信定位时，只能依赖固件侧改造（§11），v1 不做。

### 4.3 位移拆分规则

`i8` 的可表示范围是 `-128..=127`，且**突发会影响背压**，故拆分不能激进：

- 单帧步长上限 `max_step`，默认 **100**（留出安全边界，不贴 127）。
- 每帧之间等待 `frame_interval`，默认 **10 ms**。
- 一帧最多同时携带 `dx, dy, wheel, pan`（同帧移动 + 滚轮是允许的）。
- 拆分后帧数超过 `max_frames`（默认 **200**）时，工具返回参数错误而不是静默截断。

`mouse_move(1000, 1000)` ⇒ 约 10 帧（按切比雪夫距离取步数）× 10 ms ≈ 100 ms。

### 4.4 按键表达方式

工具参数用**人类可读的键名**，服务端查表转 HID KeyCode：

- 接受：`a`~`z`、`0`~`9`、`enter`、`esc`、`tab`、`space`、`backspace`、`delete`、
  `up/down/left/right`、`home/end`、`pageup/pagedown`、`insert`、`f1`~`f12`、
  `ctrl/alt/shift/gui`（默认左；`right_ctrl`/`right_alt`/`right_shift` 可用，
  但**`right_gui` 不可用** —— 它只在默认键位表里，不在 `KEY_MAPPING` 中，见 §6.4）。
- 符号：`-` `=` `` ` `` `[` `]` `\` `;` `'` `,` `.` `/`（对应 US ANSI 键位，需按 §6.4 查表）。
- `keyboard_text` 内部使用「字符 → (KeyCode, 是否需 Shift)」映射；字符不在映射表内时**整体报错**，
  不做静默跳过 —— 静默跳过会产生「看起来输入了但少了字符」的难排障行为。

### 4.5 返回格式

统一返回 `CallToolResult::success(vec![ContentBlock::text(...)])`（沿用现有代码风格）。
返回文本包含：实际下发帧数、本次 `msg_id` 区间、虚拟坐标、耗时。
失败一律用 `McpError`（`invalid_params` / `internal_error`），并在 message 里给出可操作信息
（例如「`key_code` 0x5A 不在设备键位表中，可用键：…」）。

## 5. 代码结构

### 5.1 目录结构（已实现）

```
src/
├── main.rs              # 组装：配置 → 订阅事件循环 → MCP stdio 服务
├── lib.rs               # lib target（见 5.2）
├── config.rs            # CLI 参数 / 环境变量 → Config（含 MAX_STEP <= 127 等校验 + 单测）
├── mqtt/
│   ├── mod.rs
│   ├── client.rs        # Publisher：连接状态、逐帧 publish、帧间隔休眠、后台事件循环
│   └── codec.rs         # 13B / 10B 报文编解码（纯函数 + 字节级单测）
├── device/
│   ├── mod.rs           # Devices + Sequence：虚拟光标、按下状态、动作序列独占锁、帧数预算
│   ├── mouse.rs         # split_delta / frames_needed、点击/滚轮/拖拽语义（含单测）
│   └── keyboard.rs      # 键名白名单、HID KeyCode、字符映射、组合键与文本（含单测）
└── mcp/
    ├── mod.rs           # AutoControl：合并三个工具路由 + ServerHandler + 结果渲染
    └── tools/
        ├── mod.rs
        ├── mouse.rs     # #[tool_router(router = mouse_tools, vis = "pub(crate)")]
        ├── keyboard.rs  # #[tool_router(router = keyboard_tools, ...)]
        └── system.rs    # #[tool_router(router = system_tools, ...)]
```

与原计划的两处偏差：

1. **没有 `device/throttle.rs`**。节流落地为两件事：`Publisher` 每帧后 `sleep(frame_interval)`，
   以及 `Devices` 内一把 `Arc<Mutex<()>>` 动作序列锁（保证同一时刻只有一次动作在下发）。
   单独的节流模块会多一层无收益的抽象。
2. **工具被拆到三个 `#[tool_router]` 块**（而不是单个块）：单个宏块无法跨模块，
   因此每个域用 `router = xxx_tools, vis = "pub(crate)"` 生成自己的路由，
   再由 `AutoControl::all_tools()` 用 `ToolRouter` 的 `+` 合并。
   `tests/tool_registry.rs` 锁定合并结果，防止漏挂某一域。

### 5.2 引入 lib target（已实现）

原先 crate 是**纯 binary**（无 `[lib]`），`tests/` 无法引用任何内部模块，测试只能内联。

现已新增 `src/lib.rs`，把 `config` / `mqtt` / `device` / `mcp` 作为库模块暴露，`main.rs` 退化为薄壳。

object」——这是 binary-only 时测不到的一类问题。

### 5.3 handler 组装（已实现）

沿用了 `Counter` 示范的模式，并补上 `#[tool_handler]` 的路由合并：

- 三个 `#[tool_router]` impl 块定义工具，`#[tool_handler(router = Self::all_tools())]`
- `get_info()` 里的 `with_instructions(...)` 是手写的：**新增工具必须同步更新它**
  （`src/mcp/mod.rs` 的 `INSTRUCTIONS`），否则客户端不知道设备的能力边界
- 无需 prompt，因此没有 `#[prompt_router]` / `#[prompt_handler]`

`Counter` demo 已删除：`src/common/`（rmcp 的 counter 示例）与仓库根的 `common/`（它的历史副本，

## 6. 关键子设计

### 6.1 报文编解码（`mqtt/codec.rs`）

纯函数，无 IO，便于单测：

```rust
pub fn encode_mouse(msg_id: u64, buttons: u8, x: i8, y: i8, wheel: i8, pan: i8) -> [u8; 13]
pub fn encode_key(msg_id: u64, key_code: u8, pressed: bool) -> [u8; 10]
```

测试至少覆盖：字节序、长度恒为 13/10、`buttons` 位掩码、`i8` 边界（`-128` / `127`）。

### 6.2 位移拆分

```
fn split_delta(dx: i32, dy: i32, steps: usize) -> Result<Vec<(i8, i8)>>
```

- 按切比雪夫距离 `max(|dx|, |dy|)` 决定步数 `n = ceil(max_abs / max_step)`（`frames_needed`）。
- 每步对剩余量取整除，**余数自然落到最后一帧**，保证累加后精确等于输入增量。
- 溢出保护：单帧结果用 `i8::try_from` 转换，超范围时**报错**而不是按位截断
  （例如 `split_delta(500, 0, 2)` 会被拒绝，而不是悄悄下发一个错的位移）。

`0` 位移返回空帧序列；`steps` 由上层保证 `>= frames_needed(...)`，`mouse_move_smooth` 会显式校验。
- 零位移返回空序列，工具层直接返回成功而不发报文。

### 6.3 设备侧键位表（`device/keyboard.rs`）

固件 `KEY_MAPPING` 是**服务端可用键的白名单来源**。服务端内置一份等价表
（`SUPPORTED_KEYS`，键名 → HID KeyCode），数值取自固件实际使用的 rmk 版本
（git checkout `4bbcd54` 的 `rmk-types/src/keycode/hid.rs`），**不是按 HID 规范推测的**。

> 计划里的 `--verify-keymap` 自检开关**未实现**：当前用「服务端白名单 + 查不到即报错」
> 覆盖了同一风险，启动自检没有额外价值。若将来固件键位表变更，需要
> 同步更新 `SUPPORTED_KEYS`（`tests/tool_registry.rs` 之外的 `device::keyboard` 单测
> 会校验白名单内部一致性，但无法发现与固件的偏差）。

当前固件表中的可用键：

| 分组 | 键 |
|---|---|
| 功能键 | `Esc` `F1`~`F12` `PrintScreen` `ScrollLock` `Pause` |
| 主键区 | `Grave` `1`~`0` `Minus` `Equal` `Backspace` `Tab` `Q`~`P` `[` `]` `\` `Delete` |
| 主键区（续） | `LCtrl` `A`~`L` `;` `'` `NonusHash` `Enter` `LShift` `Z`~`M` `,` `.` `/` `RShift` `Up` |
| 底部 | `LGui` `LAlt` `Space` `RAlt` `RCtrl` `Left` `Down` `Right` |
| 编辑 | `Insert` `Home` `PageUp` `End` `PageDown` `Up` |

已知固件侧瑕疵（服务端需规避，见 §10）：`Backslash` 在表中出现两次
（`keymap.rs:247` 与 `keymap.rs:342`），而 `key_code_to_pos` 用 `.find()` 取首个匹配，
故第二次登记的位置实际不可达。

**不支持的键**：小键盘（Numpad）、多媒体键、`CapsLock`、`RGui` 之外的右修饰键组合中的部分键。
`keyboard_key` 遇到这些键必须报错，而不是发出去让固件静默忽略。

### 6.4 文本输入映射

`type_text` 的实现是「字符 → (KeyCode, shift)」表：

| 字符类 | 处理 |
|---|---|
| `a`~`z` | 对应 KeyCode，无 Shift |
| `A`~`Z` | 对应 KeyCode + **按住 LShift** |
| `0`~`9` | `Kc0`~`Kc9`，无 Shift |
| `-` `=` `[` `]` `\` `;` `'` `,` `.` `/` `` ` `` `空格` | 直接对应键 |
| `!@#$%^&*()_+{}|:"<>?~` | 上述键 + **按住 LShift** |
| `\n` | `Enter` |
| `\t` | `Tab` |
| 其他（含所有非 ASCII） | **返回参数错误** |

非 ASCII 报错的原因是硬约束：设备只有 US ANSI 键位表、无输入法、无 Unicode 注入通道。
若后续确需中文输入，唯一可行路径是在被控主机侧挂输入法，由本服务端只负责按键序列（§11 待确认项）。

### 6.5 节流与背压控制（实现说明）

- **动作序列串行化**：`Devices` 持有一把 `Arc<Mutex<()>>`，每次动作先 `lock_owned()` 取得
  `Sequence`（`src/device/mod.rs`）。鼠标与键盘帧因此不会交错，帧间隔也才真正起到限速作用。
  一次长拖拽会独占整个序列（这是刻意的）。
- **它不管「动作之间的顺序」**：rmcp 并发派发工具请求，谁先拿到锁不确定（实测见 §10 / R14）。
  需要顺序的组合动作必须由客户端串行调用。
- **逐帧节流**：`Publisher` 每发出一帧就 `sleep(frame_interval)`（默认 10 ms），
  与 §3.4 的通道容量 8 匹配。
- **帧数预算**：每个动作在下发前调用 `check_budget(frames)`，超过 `max_frames`（默认 200）
  直接报错而不截断。
- **broker 未连接时快速失败**：不排队等待重连 —— rumqttc 会把请求缓存到恢复后补发，
  那会让几秒前的动作突然生效。错误信息里直接给出 broker 地址与原因。

## 7. 配置与运行

### 7.1 配置项

MCP stdio 服务端**不能向 stdout 写任何非协议内容**，因此配置只能走 CLI 参数与环境变量
（不要引入会打印 banner 的初始化逻辑）：

| 项 | 环境变量 | CLI | 默认 |
|---|---|---|---|
| Broker 地址 | `MCP_MQTT_BROKER` | `--broker` | `192.168.3.15` |
| Broker 端口 | `MCP_MQTT_PORT` | `--port` | `1883` |
| 鼠标主题 | `MCP_MOUSE_TOPIC` | `--mouse-topic` | `mouse/auto` |
| 键盘主题 | `MCP_KEYBOARD_TOPIC` | `--keyboard-topic` | `keyboard/auto` |
| 本端 client id 前缀 | `MCP_CLIENT_ID` | `--client-id` | `mcp-auto-control` |
| client id 附加 PID | `MCP_UNIQUE_ID_SUFFIX` | `--unique-id-suffix` | `true` |
| 帧间隔 | `MCP_FRAME_INTERVAL_MS` | `--frame-interval-ms` | `10` |
| 单帧最大步长 | `MCP_MAX_STEP` | `--max-step` | `100` |
| 单次调用最大帧数 | `MCP_MAX_FRAMES` | `--max-frames` | `200` |
| 虚拟光标起点 | `MCP_MOUSE_ORIGIN` | `--mouse-origin` | `0,0` |

**为什么 client id 要带 PID 后缀**：MQTT 以 client id 标识会话，重复的 id 会让
broker 踢掉旧会话。实测（`mcp-auto-control` + WorkBuddy 预热池）两个实例同用默认
id 时，连接会以约 0.5~1 秒的周期在两个 PID 之间来回易主，表现为 `device_status`
的「已连接/未连接」在相邻两次查询间跳变、工具调用时好时坏。附加 PID 后各实例
持有独立会话。若确实需要固定 id（例如设备侧按 id 做了鉴权），用
`--unique-id-suffix false` 关闭——但此时**必须**为每个实例显式设置不同的
`--client-id`。当前 client id 可在 `device_status` 中查看。

### 7.2 启动行为

1. 解析配置 → 建立 MQTT 连接（失败时不立即退出，保持重连，以免 MCP 客户端因启动即崩而反复重启）
2. 注册工具 → 以 stdio 提供 MCP 服务（沿用 `Counter::new().serve(stdio())` 的写法，`src/main.rs:20`）
3. 日志一律走 **stderr**（现有 `tracing_subscriber` 配置已经如此，保持不变）

### 7.3 客户端接入

MCP 客户端配置示例（stdio）：

```json
{
  "mcpServers": {
    "auto-control": {
      "command": "E:/path/to/mcp-auto-control.exe",
      "env": { "MCP_MQTT_BROKER": "192.168.3.15" }
    }
  }
}
```

## 8. 安全与可靠性

自动控制鼠标键盘是**会直接作用于真实桌面**的能力，需要一个明确的刹车机制。

### 8.1 前置条件

- 被控桌面必须处于「可接受自动输入」的状态（未锁屏、焦点窗口正确）。
  服务端无法校验这一点 —— 这是使用者的责任，需在 `README.md` 与工具描述中写明。
- broker 无鉴权，同网段任何人可发布同样报文。**应在受控网络内运行**。

### 8.2 参数校验

- 所有数值参数做范围校验（`dy/dx` 的绝对值上限、`count` 上限、`interval_ms` 上下限）。
- 文本长度上限（建议 512 字符），超限报错。
- 拒绝会产生超限帧序列的请求（§6.5）。

### 8.3 `emergency_stop`

必须实现且优先实现：一次调用完成

1. 向 `keyboard/auto` 发送当前**所有已按下键**的松开报文（含 LShift 等修饰键）
2. 向 `mouse/auto` 发送 `buttons = 0` 且各增量为 0 的报文

服务端需在内存中维护「已按下键集合」与「已按下鼠标按钮集合」，读操作（`device_status`、`emergency_stop`）
依赖该状态。这也解释了为什么不能让 MCP 层直接发送裸帧 —— 状态必须被集中跟踪。

**能力边界（必须写进工具描述）**：`emergency_stop` 只解除**服务端自己**按下的键与按钮。
它无法覆盖物理按键（§3.7），也无法撤销已经生效的 OS 侧动作（例如已经触发的快捷键）。
因此它的描述里不能出现「保证停止一切输入」这类承诺。

### 8.4 软确认与可观测性

由于 §3.5 的限制，服务端无法确认执行结果，v1 采取：

- 每次工具调用返回本次使用的 `msg_id` 区间与帧数，便于与设备串口日志对账。
- `device_status` 返回 broker 连接状态、已按下集合、虚拟坐标；**明确不声称设备在线**。
- 一次调用下发大量帧时，若队列积压超过阈值（如 500 ms 未清空），返回 `internal_error` 提示节流。

### 8.5 测试策略（现状）

|---|---|---|
| 单测 | 报文编解码字节级断言（含 i8 边界、长度恒为 13）；位移拆分累加不变量与溢出拒绝；键名白名单唯一性与归一化；ASCII→Shift 表 | ✅ 29 个单测已实现 |

## 11. 待确认与固件侧依赖

以下项**不由本仓库解决**，需与固件维护者确认后才能推进。编号被 §10 的风险表引用。

#### 11.1 增加状态/确认主题（消除 R1）

建议 `mouse/status`、`keyboard/status`：设备上线/离线用 LWT 通告，关键动作用 ACK 回应。
这是唯一能从根本上区分「报文丢了」与「设备没收到」的路径。

#### 11.2 修正长度校验（消除 R2）

`AutoMouse/src/mqtt.rs:147` 的 `payload.len() >= 10` 应改为 `>= 13`（或改用 `payload.get(12)` 这类安全取值）。
当前实现是可被任意发布者触发的**远程复位**。

#### 11.3 `client_id` 可配置（消除 R4）

支持多板共存；固件源码内已有两处 `TODO` 标注同一问题。

#### 11.4 `KEY_MAPPING` 去重与补全（缓解 R7）

`Backslash` 重复登记（`keymap.rs:247` 与 `keymap.rs:342`），`key_code_to_pos` 用 `.find()` 取首个匹配，
故第二次登记的位置不可达。另外 `RGui`、`CapsLock`、小键盘、多媒体键均不在表内。

#### 11.5 broker 参数运行时可配

固件 README 已将其列为后续计划；当前换网络必须重新烧录。

#### 11.6 产品决策待确认

- 是否需要**绝对坐标定位**（决定是否需要固件上报光标位置，对应 R6）？
- 是否需要**中文/Unicode 输入**（决定是否要在被控主机侧引入输入法协同，对应 R8）？
- 是否需要支持**超过一对**鼠标/键盘设备（对应 R4）？

#### 11.7 安全边界待确认

本服务是否只在本机/受控网络使用？是否需要为高风险动作再加一层确认机制
（例如要求 MCP 客户端在调用 `keyboard_text` / `mouse_drag` 前显式二次确认）？
另需确认：设备按键在有人员操作时是否会被「物理输入 + 远程输入」同时驱动（R12），
使用规范上是否需要约定「自动控制期间设备按键无人触碰」。

## 12. 附录

### 12.1 报文示例

鼠标移动到右下方并单击左键（`+100, +50`）：

```
topic: mouse/auto
payload (13B): 01 00 00 00 00 00 00 00  64 32 00 00 00
               └──── msg_id = 1 ────┘  ▲  ▲  ▲  ▲  ▲
                                      btn x  y whl pan
                                      =0  =100=50 =0 =0
```

按下 A 键（HID KeyCode `0x04`）：

```
topic: keyboard/auto
payload (10B): 02 00 00 00 00 00 00 00  04 01
               └──── msg_id = 2 ────┘  ▲  ▲
                                    key pressed=1
```

### 12.2 设备侧不可用键（核实结果）

以下键**不在** `KEY_MAPPING` 中，下发后会被固件静默忽略，服务端必须直接报错：

| 键 | 核实方式 |
|---|---|
| `CapsLock` | 全表检索无此项 |
| `RGui`（右 Win） | 仅在默认键位表出现（`keymap.rs:464`、`:472`），不在 `KEY_MAPPING` 中 |
| 小键盘 `Numpad*` | 全表无 Numpad 键值 |
| 多媒体 / 音量键 | 全表无对应键值 |
| 层切换键 `mo!(1)` | 属层动作而非 KeyCode，无法通过 `key_code` 表达 |
